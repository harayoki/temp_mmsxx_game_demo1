# サウンドツール — コンセプト

**まだ実装していない。** ここは決めたことと未定を置いておく場所。
サウンドを別リポジトリへ切り出す案は**別途**まとめる。

## 動かさないルール

**迷ったらここへ戻る。** 以下は個別の機能ではなく、**判断の物差し**。
新しい思いつきがこれに反するなら、思いつきのほうを捨てる。

(**最初のうちは動く。** 固まるまでは書き換えてよい。
固まったあとは、動かすときに「なぜ動かすか」をここへ書き足すこと)

### 大原則 — あとからできることは、全部あとからやる

調も、音階も、拍子も、音色も、機種も、エフェクトも、**先に決めさせない**。
決めた瞬間に選び直せなくなるものを、作る手前に置かない。

**下のルールのほとんどは、ここから落ちてくる。**
部品を C で持つのも、進行が原型を保つのも、機種を最後まで選ばないのも、
全部「あとから変えられるようにするには、そうするしかない」から。

新しい機能を思いついたとき、まずこれで測る —
**それは、あとから決められる形になっているか。**

**1. フルプロシージャル。楽譜もピアノロールも出さない**

音符を 1 つずつ置く画面は作らない。曲は**規則と部品**から組み立てる。

**規則で作れるものは規則に任せ、人間的なところは MML の部品が吸収する。**
手癖・崩し・掴みは規則にならないので、部品として置く。**この 2 つで全部をまかなう。**

プリセットが揃っていれば **MML を 1 文字も書かずに作れる**のが目標で、
部品箱の充実そのものが機能。

**乱数を使うものは必ず種(シード)を持つ** — ゆらぎも、ランダムボタンも、
生成パートの崩しも。持たないと鳴らすたびに変わり、あとから戻せなくなる。

**2. 原型を壊さない**

部品は **C のキー・基準の拍子**で保存する。進行は**素直な原型**を保ちつづける。
調・音階・拍子・エフェクト・代替コードは**すべて上に重ねる変換**で、
**焼くのは出力のときだけ**。だから何をどう変えても元へ戻せる。

**3. 汎用で作り、機種は出力の都合**

作曲中はどの機種・音源かを気にしない。独自音源を持つのは機種の山を越えるため。
降ろすのは**音のマスク**(8 音を 3 音へ)と**音色の変換表**の仕事。
**最初に機種を選ばせない。**

**4. 全部テキスト**

プロジェクトの形式 = 書き出しの形式 = テキスト。
差分が読めて、AI にそのまま渡せて、git に置ける。
PCM すら波形を抱えず、**作り方**を持つ。

**5. 芯が 1 つ、顔が 4 つ**

MCP・API・CUI・画面。**画面なしで全部できる**芯を下に置く。
画面はその 1 つの顔にすぎない。

**6. AI はツールに載せない**

**AI が作るのは部品と規則。ツールが持つのは実行。**
実行時に AI を呼ばない(再現しない・オフラインで止まる・鳴らすたびに変わる)。
外から叩く口(MCP / API)は最初に用意する。

**7. 勝手に詰めない。人が解くための道具を置く**

マスクで音があふれても自動で埋めない。代わりに `q` で短くする・少し後ろへずらす、
という**人が解く道具**を用意する。ランダムも「いい曲を出す」のではなく
**叩き台を出す**もの。

**8. コンセプトに合わないことは、別のツールに任せる**

道具を曲げて機能を入れない。外へ出す。**すでにそうしているものが並んでいる。**

| 外に出したもの | 任せる先 |
| --- | --- |
| 音色作り(波形メモリ / FM) | 別の道具 |
| SE と TALK | 別の道具 |
| PCM の作り方 | 別ツールで補佐 |
| 機種ごとの曲ファイル(NSF / GBS / SID) | DefleMask(と Furnace) |
| 曲の仕上げ・盛り | DTM |
| 曲想の判断・凝ったフレーズ | 外から口を叩く AI |

**この道具が持つのは、曲の組み立てだけ。**

## 他の作曲ソフトとの違い

上のルールを外から見たもの。

- **MML ベースである** — テキストのまま人にも AI にも渡せる
- **AI 連携がネイティブ** — 後付けのプラグインではなく、口が先にある
- **プロシージャルな作曲構成** — 部品と条件と規則で組み立てる
- **原型を壊さない** — トラッカーも DAW も破壊編集が基本で、
  「原型」という概念を持たない。**ここがいちばん効く**
- **機種を後から選べる** — FamiTracker も DefleMask も
  **最初にチップを選んでから作りはじめる**。この道具は最後まで選ばない
- **git に置ける** — トラッカーのプロジェクトはバイナリ。
  曲をコードと同じように扱える
- **転調が楽** — 部品が C で、調は着せるもの。**転調は着せ替えであって打ち直しではない**。
  トラッカーでも手書き MML でも、転調は書き直しになる
- **思想が逆を向いている** — 自動作曲ソフトは「いい感じにやってくれる」が売り。
  この道具は**人が解くための道具**を置く

## これは何か

**MML の部品箱と組み立て表。** 楽譜もピアノロールも出さない。
DTM のようなスコア入力もしない。**曲の組み立てだけ**を見る道具。

目標は **プリセットが揃っていれば MML を 1 文字も書かずに曲が作れる**こと。
部品箱の充実そのものが機能であり、道具の出来を測る物差しになる。

**フルプロシージャルで作り、人間的なところは MML の部品が吸収する。**
規則で作れるものは規則に任せ、規則にできないもの(手癖、崩し、掴み)は部品として置く。
**この 2 つで全部をまかなう。**

手作業版はすでにある。[demotunes.js](../engine/util/demotunes.js) の `beatTune()` が
`BEAT_KICK_A` `BEAT_SNARE_A` `BEAT_HAT_A` `BEAT_TOM_FILL` を定数にして
8 小節ぶん並べており、コメントには進行(Dm Dm B♭ C Dm Dm Gm A)まで書いてある。
**ツールはこれを画面でやるもの**で、既存曲がそのまま最初の題材になる。

## 最初に作るもの

**アクションゲームの BGM。ファミコンディスクシステム(FDS)想定。**
**サンプル曲をツールに同梱する。**

FDS はこの道具の最初の的としてよく合っている。

- FDS の目玉は **波形メモリのチャンネル**(RAM アダプタの 2C33 が 1 本足す)。
  engine の `wt*` がまさにそれで、道具立てがもう揃っている
- 声の並びは **矩形波 2 + 三角 + ノイズ + FDS 波形 = 5 声**(ほかに DPCM)。
  **マスクの目標が 8 音 → 5 音**とはっきりする
- FDS の変調ユニットは**音程と音量を揺らす**。`@v`(ビブラート)が近い

**ただし枠が違う。** FDS の波形は **64 個・6 ビット(0〜63)**。
今の `registerWave` は 32 個・5 か 8 ビットなので、実機に寄せるなら枠を足すことになる。

同梱するサンプル曲は、**デフォルトへの昇格路の最初の中身**になる。
既存の `beatTune()` がそのまま題材になる。

**サンプル曲その 2 — クラシック曲のイマドキアレンジ。**

これは**道具の売りをそのまま実演する**。原型(古典の旋律)を C の部品として持ち、
音階・進行・ドラムの分野・拍子を差し替えて今風にする。
**「原型を壊さない」と「あとから何でも変えられる」が、聴けば分かる形になる。**
著作権が切れているので、同梱にも困らない。

サンプル 1(FDS のアクション BGM)は**「チップチューンが作れる」の証明**、
サンプル 2 は**「変えられる」の証明**。見せる筋が違うので、2 つで一組。

**サンプル曲その 3 — ホラー音楽。難しそうなので、だめなら途中でやめる。**

これは**道具の限界を試すもの**で、詰まりそうなところが最初から見えている。

- **無調** — 調の枠から外れる。ただし**音階の切り替え**があるので、
  半音階・全音音階・オクタトニックを音階として持てば乗るかもしれない
- **不協和音** — 和音エフェクトのアルゴリズムに「濁らせる」種類を足す話になる
- **SE が主役になりがち** — SE はルール 8 で外へ出したもの。
  ホラーは曲より音響の比重が大きいので、**ここで詰まるなら詰まって当然**
- **「間」と持続音が主**で、部品を並べるモデルとそもそも相性が悪い

**やめてよい。** どこで詰まったかが、そのまま仕様の穴か、
**「外に出した判断が正しかった」の確認**になる。

**サンプル曲その 4 — アイドル曲。作りたくはないが、外部連携のテストとして。**

あとから声を別のソフトで乗せる(ずんだもん / VOICEVOX でもよい)。
**ねらいは曲そのものではなく、外へ渡す道の確認。**
DTM や DefleMask とは渡す相手の種類が違うので、**ルール 8 の実例がもう一筋増える**。

渡すのは**メロディと歌詞のタイミング**(MIDI が素直)。

ひとつ制約が読める。**声が乗る旋律は、チップチューンの旋律とは違う。**
人の声域はせいぜい 1.5 オクターブで、1 音 1 モーラ。
跳躍の激しい旋律や細かすぎる音符は、そのままでは歌えない。
**「歌える形へ畳むフィルタ」**が要るかもしれない(音域を折り返す / 細かい音をまとめる)。

engine の TALK は使わない。**歌は外のソフトに任せる**(ルール 8)。

## 部品の種類は 3 つ

**旋律 / 和音・ベース / 打楽器。** 進行をいじったときの追従が、種類でほぼ決まる。

- **打楽器** — 進行を見ない。フィルタも通さない
- **和音・ベース・生成パート** — **進行を見る。度数で書くので必然的に追従する。**
  代理コードに差し替えた瞬間にベースが歩き直すのが値打ち
- **旋律** — **ここだけ、どちらもありうる**

つまり**スイッチが要るのは旋律だけ**で、あとは種類から自動で決まる。
2 種(音程あり / 打楽器)では旋律とベースの区別がないので、全部を手で指定することになる。
**だから 3 種。**

### 旋律の追従は 3 段

「する / しない」の 2 択より、段に切るほうが実用的。

1. **追従しない**(そのまま)— **リハーモナイゼーション。**
   同じ旋律が別の色に聞こえる。「あえて和音だけ変える」がこれ
2. **外れた音だけ寄せる** — コードトーンから外れた**長い音だけ**直す。
   短い経過音は外れたままでよい。**いちばん使えるのがここ**
3. **全部コードトーンへ寄せる** — 安全だが、**もう別のメロディ**になる

### 既定はロック(追従しない)

- **大原則**(あとから決められる)— 追従を既定にすると、進行をいじるたびに旋律が
  勝手に変わり、**原型が見えなくなる**。「和音だけ変えて聴き比べる」ができなくなる
- **ルール 7**(勝手に詰めない)— 同じ思想。寄せるのは人が選んでかけるフィルタ

## 部品

- **C のキーで、音程の動きだけ**を持つ。出だしのオクターブ・音色・音量・ゲートは
  組み立て側で着せる。同じ部品を別の音色で使い回せる
- 並べ方は**長さ任せ**。扱うときに小節へフィットさせられるようにする
- **打楽器の部品はフィルタを通さない。** `BEAT_NOISE` の `o2` `o5` `o6` は
  音の高さではなく「バスドラの胴 / 砂 / シンバル」という役割で、
  `BEAT_KICK` の `c8` も高さに意味がない。転調に巻き込むと壊れる
- **プリセットを豊富に用意し、それぞれに分野を設定する**
- **ランダムボタン**で同じ分野から引いて適当につないでくれる。分野をまたぐのも可
- ドラム部品は**雰囲気**もパラメータに持つ(静か / 盛り上げ / 終わった感じ)。
  置いたあとから「ここは落とす」「ここで上げる」「ここで締める」を効かせられる
- したがって**マスに置くのは部品そのものではなく条件(分野 + 雰囲気)**で、
  実体はツールが選ぶ
- エフェクトを適用した結果を**新しい部品として登録できる**。
  ただし保存は **C に換算し直す**。部品箱の中身は必ず C で揃う

## ランダムが入口

**とにかくランダムボタンを押すと、何かできる。**
白紙を見せない。**気に入ったものが出たら、そこから調整を始める。**

- ランダムは**それぞれ個別に振れる**(ドラムだけ / ベースだけ / 進行だけ / 旋律だけ)
- **振ったシードは記録する**
- **まとめて振り直すやつが要る**

**曲のシード 1 つから各パートのシードを導く**形にすれば、
一発で全部を振り直せる。個別に振り直したところだけ、別のシードを持つ。

### 乱数は 2 種類ある。混ぜない

**部品が増えるとシードとの対応が壊れる。**
ライブラリに部品が足され、デフォルトへ昇格すると母集団が変わるので、
**同じシードが別の部品を引く**。だから分ける。

**1. ライブラリから引く乱数** — 母集団が変わると壊れる。
**シードではなく、引いた結果を書き留める。**
どの部品を選んだかをプロジェクトに書く。全部テキストなので大きさは問題にならず、
むしろ**人が読める**(何が使われているか見える)のは得。
**ライブラリがいくら増えても曲は動かない。**

**2. 数値をばらす乱数** — ゆらぎ(音痴)、崩し、生成パートのばらつき。
母集団が無いので、**シードのままで完全に再現できる**。

**シードは「振るための道具」であって「再現の手段」ではない。**
振ったときのシードを添えておくのは無害で、「同じ振り方をもう一度」には使える
(ライブラリが同じなら)。

つまり曲は **「引いた結果 + 調整 + ゆらぎのシード」** で表せる。

### 触ったところは振り直しに巻き込まない

「気に入ったら調整を始める」を成り立たせるには、
**調整したところが振り直しで消えてはいけない**。
消えるなら、調整するたびにランダムが使えなくなる。

なので**ロックが要る**。旋律のロック、置いた部品を動かさない、と同じ思想で、
道具全体を通して一貫している。**触ったら鍵がかかり、鍵は目に見えて外せる**のがよさそう。

## 曲の骨格

- **コード進行が土台。** ただし**コード自体は鳴らさなくてよい** — 進行は枠であって音ではない
- 進行は**素直な原型を持ちつづける**。代替コードへの置き換えや分割など
  高度な理論を上に重ねられるが、**いつでも原型へ一発で戻せる**
- **調と音階は区間ごと**に持つ。音階はワンタッチで切り替えられる

### 音階はセントで持つ

半音の並び(`0,2,4,5,7,9,11`)ではなく、**セントの並び**(`0,200,400,…`)で持つ。
実装のコストはほとんど変わらないのに、**マカームもガムランも同じ入れ物に入る**。

**いま微分音に対応すると決めるわけではない。入れ物だけ開けておく**(大原則)。
半音で持つと、あとから足すには音階の型を作り直すことになる。

- **鳴らす側はそのまま反映できる。** engine は周波数を自分で計算しているので、
  セントを乗せるだけ。`@d`(デチューン)もセント単位なので単位がそろう
- **書き出し先が扱えるかは分からない。**
  扱えないところは**音色の変換表と同じ理屈で、近い半音へ丸める**

### 民族音楽はどこまで乗るか

**未対応でよい**が、境目を控えておく。

**乗る** — 音階が違うだけのもの(都節・琉球・ヨナ抜き・ペンタトニック・
ヒジャーズ・ブルース)、リズムが違うもの(クラーベ、ボサノバ、5/8 や 7/8 の変拍子)、
ドローン(長い音を 1 声置くだけ)。

**乗らない** — 微分音と音律の違い(入れ物だけセントで開けておく)、
拍が伸縮するもの(追分様式やアーラープの自由リズム。拍のグリッドに乗らない)、
和声を持たない構造(進行を 1 つのままにすれば実害はない)、
奏法が音色そのもののもの(尺八のムラ息、三味線のサワリ。ルール 8 で外に出したもの)。

**有名なコード進行はライブラリに持っておく。**
カノン進行、王道進行、循環、ブルースの 12 小節、ii-V-I など。

**度数(ローマ数字)で持てば調に依存しない。**
部品を C で持つのとまったく同じ正規化で、調は区間が着せる。
おかげで**進行を丸ごと差し替えて聴き比べられる** —
カノン進行で作った曲を王道進行へ、が一発で通る(大原則そのまま)。

### 転調は一級で扱う

**転調しまくる曲が好きなので、隅に置かない。**

そして**この道具はもともと転調に強い**。部品を C で持ち、調は区間が着せるので、
**転調は着せる調を変えるだけ**で、音符の書き直しが要らない。
トラッカーや手書き MML では転調は打ち直しになる。ここは素直に差になる。

**持ち方は 2 つを両方持つ。**

- **区間が調を持つ** — 大きな転調(A メロとサビで調が違う、など)
- **進行そのものが調の動きを含む** — 「Ⅰ→Ⅵ→…→半音上げて繰り返し」のように、
  相対的な調の動きを進行プリセットが持つ。**組み立て表を細かくせずに済む**

**転調のやり方もライブラリに持つ。** 有名進行ライブラリの兄弟として:
直接転調、ピボットコード(共通和音で自然に移る)、ドミナントで橋渡し、
半音上げ / 全音上げ、同主調へ(メジャー ⇄ マイナー)、平行調へ。

**両方書いてあったら、区間が土台で、進行はそこからの相対。**

区間が「C」、進行が「半音上げて繰り返す」なら **C → C# → D → D#**。
区間を D に変えれば **D → D# → E → F** とまるごとついてくる。

進行を度数(ローマ数字)で持つと決めた時点で、**調の動きも相対で持たないと噛み合わない**。
部品を C で正規化しているのとまったく同じ理屈で、ここは導き出される答え。

部品が「C の原型 + フィルタ」なのと同じ形。
**原型は壊さず、変換を上に重ね、出力のときだけ焼く**で全体が通っている。

### 進行は木で持つ

**代理コードで 1 つを 2 つに割り、そのそれぞれをまた割る。**
これを繰り返すだけで楽しい、というのが**この道具の遊びの核**になりそう
(ランダムボタンと並ぶ、触っていて楽しいところ)。

繰り返し効くものなので、**進行は平らな並びではなく木**で持つのが素直。

- 原型の 1 コードが根。割ると子ができる
- **枝を畳めば 1 段戻る。全部畳めば原型**
- 「原型を壊さない」が、そのまま入れ物の形になる

平らな並びで持つと割った履歴を別に抱えることになり、戻すのが面倒になる。木なら畳むだけ。

割りすぎ防止に**拍の下限**だけ決めておく(1 拍より細かく割らない、など)。

### 拍子

MML に拍子は無い(小節線 `|` は読み飛ばされる)ので、**完全にツール側の概念**。
**調とまったく同じ形にする。**

- 部品は**基準の拍子で保存**し、**拍子は組み立て側で着せる**
- 拍子は**区間ごと**に持つ(調・音階と同じ場所)。曲で 1 つにすると変拍子ができない

あとから変えるときの変換は 3 系統。

- **ドラムは変換せず引き直す。拍子ごとにプリセットを持つ。**
  3 拍子のビートは 4 拍子を削ったものではなく、別のパターン。
  マスに置くのが部品ではなく**条件**だという決めが、ここで効く
- **旋律とベースは 2 通りあるので選ばせる** —
  拍を足し引きする(4 → 3 で 4 拍目を落とす / 前の音を伸ばす。曲の感じが残る)か、
  音価を伸縮する(中身を 3/4 倍に詰める。並びは残るがノリが変わる)か
- **進行は割り当てそのまま。** 小節の長さだけ変わる

**部品は拍数を持つ。** 持たないと拍子の変更にもランダム接続の拍そろえにも追従できない。
逆に持てば**両方いっぺんに解ける**。

ドラムのプリセットは **分野 × 雰囲気 × 拍子の 3 軸**になる。全部埋めなくてよく、
4/4 を厚く他は薄くでよい。

**在庫が無いときは「ここは未定」を選べるようにする。**
崩したり詰めたりせず、**穴を穴のまま置く**。TODO として残り、あとで埋める。
**これはドラムに限らず、どのパートでも同じ。**

大原則(あとからできることは全部あとからやる)の極みで、
**未定を未定のまま持てる**。ルール 7(勝手に詰めない)ともそのまま合う。

## フィルタとエフェクト

- 転調とスケール変換は**組み立てで焼き込む**。出力は変換済みの MML 文字列で
  `defineBGM` にそのまま渡せる。**エンジンは無改造**
- リズムはそのままで音程だけずらす / 音程はそのままでリズムをずらす
- **エフェクト指定**で書く。デチューンは実際には 2 音鳴るが、エディタ上では 1 つ。
  今の `@d` `@o` `@s` がすでにその作りで、**1 チャンネルの指定が実際には
  2〜4 音を食う**([audio.js](../engine/audio.js) の `_scheduleTrack` 付近)。
  マスクの数えかたにも、他の MML 系へのコンバートにも効く
- **適当に和音を鳴らすエフェクト**もある(決め方のアルゴリズムを持つ)
- **少し音痴にする**(ゆらぎ)。音程・タイミング・音量をわずかにばらす

**わざとの音痴と、実機の音痴は別のもの。**
エンジンにはすでに実機由来のものがある(`psgSnap` が実機の階段へ丸めるので、
高い音ほど狂う = 音痴に聞こえる)。あれは**機種の都合**で、こちらは**表現**。
混ぜずに別々に持つ。

### 乱数を使うものは必ず種(シード)を持つ

ゆらぎのエフェクトも、ランダムボタンも、生成パートの崩しも。

持たないと鳴らすたびに違う音になり、**ルール 6 とまったく同じ穴にはまる**
(再現しない・鳴らすたびに変わる)。
種があれば「さっきのゆらぎをもう一度」ができ、引き直した結果も捨てずに戻せる。
**大原則(あとから決められる)にも、これが要る。**

engine には [rng.js](../engine/rng.js) がある。

### 作曲テクニックはエフェクト一本でいく

**MML を書き換える機能は作らない。**
「エフェクトの結果を新しい部品として登録できる(C 換算で保存)」が、その役をすでに果たす。
ふだんは非破壊で乗せて率を変えて試し、気に入ったら**焼いて部品にする**。
一方通行で足りるので、二重に作らない。判定は「あとで外したくなるか」だけ。

技術は**かかる場所で 3 つに分かれる**。

1. **部品にかかるエフェクト** — スウィング(8 分を 3 連の 2:1 へ寄せる。**率で持つ**)、
   ゴーストノート、リズムずらし
2. **進行の層** — テンション(7th / 9th / 13th)、ii-V-I への分割、代替コード。
   **すでにある「原型 + 置き換え」に乗る**ので、新しい仕組みは要らない
3. **生成パート** — 下記

### 生成パート(部品でもエフェクトでもない第 3 の種類)

**進行を見て、その場で作るもの。** ウォーキングベース、コード刻み、アルペジオ、
和音のボイシング(ドロップ 2 など)。
「適当に和音を鳴らすエフェクト」の正体はこれで、部品箱から引くものではない。

- **進行が変わったらついてくる**のが値打ち。代替コードへ差し替えた瞬間に
  ベースが歩き直す。**あとから決められる**が、ここでも効いている
- したがって**実行時に AI は呼ばない**。呼ぶと再現しない・オフラインで止まる・
  鳴らすたびに違う曲になる。芯の方針(全部テキスト / どこでも動く / CUI でも動く)とも合わない

**AI の持ち場は、部品と規則を作ること。**

- 追従が要らないもの(凝ったフレーズ、変わったオカズ、イントロの掴み)は
  AI が作って**部品として置けば、あとはただの部品**
- ジャンルごとの生成規則(ジャズのウォーキングベース、ボサノバの刻み)は
  AI に考えさせて**テキストの規則としてライブラリに保存**する。
  ツールはそれを**実行するだけ**で、実行時に AI は要らない
- よくできた規則は**デフォルトへ昇格する**(部品と同じ道)

**AI が作るのは部品と規則。ツールが持つのは実行。**

### スマートベース

ドラムとベースはかみ合わせが多い。**ドラムとかみ合うベースを「スマートベース」と呼ぶ。**

生成規則が**進行に加えてキックの位置を見る**。
ベースはもともと進行を見る種類なので、**見る先にドラムを足すだけ**で済み、
仕組みが増えない。セットの部品にすると組み合わせの自由が消えるので、そうしない。

**かみ合わないベースは、別に作る。** ふつうの部品として置いたベースは
ドラムを見ないし、進行にも追従しない。旋律のロックと同じ思想で、
**置いたものは勝手に動かさない。**

**エフェクトには 2 つの層がある。名前を分ける。**

1. **譜面エフェクト** — MML に焼けるもの(転調・スケール・ずらし・スウィング など)
2. **盛り** — MML に落とせないもの。再生時や WAV 書き出し時にかける

書き出し先で扱いが分かれる。**盛り**は WAV / MP3 には乗るが、
MML 系や機種向けのデータには乗らない。**どちらの層か**を持たせておく。

## 音源と機種

- **作曲中はどの機種・音源かを気にしない。** 汎用のまま持ち、書き出すときに各機種へ降ろす
- **独自音源を持つのは機種の山を越えるため**
- 音色は**タグで分類**する(「ファミコン対応」など)。これが出せる / 出せないの判定になる
- 出せない音色は**近いものへ自動で振り替える**。その**変換表は自動で作られ、
  プロジェクトに保存する**(一度できた対応をあとから直せて、次の書き出しでもその通りになる)
- **チップチューンが主**。そのうえで **PCM 扱いで生音もサポート**する。
  ただしツールの音源そのものには **PCM を積まない**。
  書き出すデータの中で PCM を指定するのはかまわない

**再生のときに外部の WAV を重ねられるようにするかもしれない。**
外で作った歌(サンプル 4)や生音を、曲と一緒に聴いて合わせるため。
engine には音声ファイルの BGM(`defineBGM({url})`)がすでにある。

- **プロジェクトは WAV の中身を抱えず、置き場所だけ指す。** ルール 4 を壊さない
- 書き出しでは VGM や .dmf に乗らず、**WAV 書き出しのときだけ混ざる**
  (MML に落とせないエフェクトと同じ扱い)

**強く考察する音源**

- MSX / ファミコン / ファミコン特殊音源 / PC エンジン / ゲームボーイ /
  アーケードのナムコ初期、その周辺
- MSX はデューティ比を持たないが、**レジスタ操作で行けそうならその手で出す**
- スーファミ以降やメガドライブは、AI で考察できるなら対応(土地勘の外)

前者の一群は、今のエンジンが持っている道具立て(矩形波のデューティ比・三角・ノイズ・
波形メモリ・2 オペ FM)でほぼ覆える。**汎用音源の形が、すでにこの一群の最大公約数になっている。**

## 音のマスク

- 優先度をつけて **8 音を 3 音へまとめる**。音の薄いところの空きチャンネルへ差し込む
  (スターソルジャーがこの作り)
- 参考: ミロンの冒険のボーナス面。音源が多く聞こえるが通常のファミコンだけで、
  **ベースと高い音を時間で分け合っている**
- **勝手に詰めなくてよい。** 代わりに人が調整しやすい道具を置く:
  **音を短くする(`q`)** / **少し後ろへずらす**
- `q` はすでに MML にある([mml.js](../engine/mml.js))。
  **少し後ろへずらす指定は今は無いので足す**

**マスクは書き出しのときだけでなく、ふだんからかけて作る。**

3 音に絞ったまま作れば**要素を足しすぎようがない**。
制約がそのまま作曲を良くする、というやつ。

ただし**マスクは決定ではなく聴き方**。原型は 8 音のまま残っていて、
いつでも外せるし本数も変えられる。だからふだんからかけても
**大原則(あとから決められる)を破らない**。
ルール 3(最初に機種を選ばせない)ともぶつからない —
**「3 音で聴いてみる」であって「3 音の曲にする」ではない。**

汎用で作ることと機種の制約へ降ろすことをつなぐ要。
考え方は SE の席の取り合い(`_victim`)と同じ。

## 書き出し

- ゲーム用データ / WAV / MP3 / MIDI / DefleMask(.dmf) / レジスタ系(VGM など)
- MSXplay のような **MML 系とは、取り込みと書き出しの両方**ができる
- FamiStudio も手元にあるが、**そこを経由する必要はない**。
  機種向けは「**エミュレータで鳴らせる形で出せればそれでいい**」
- WAV は [wavexport.js](../game/wavexport.js) がオフラインレンダリングで作れる。
  **MP3 だけはブラウザ内にエンコーダを持っていない**ので足しものが要る

**エミュで鳴らす形には 2 通りある。手間がまるで違う。**

- **レジスタの記録(VGM)** — いつどのレジスタへ何を書いたかを時間順に並べただけのもの。
  この道具は自分が何を鳴らしているか全部知っているので、**そのまま書き出せる**。
  多くのチップを 1 つの形式で覆えるのも強み
- **機種ごとの曲ファイル(NSF / GBS / HES / KSS / SID など)** — これは**データではなくプログラム**で、
  中に音楽ドライバが入っている。出すには**その機種の機械語でドライバを書く**ことになる

**自前で出すのは VGM だけにする。** 保守が重くなるので、機種ごとの曲ファイルは書かない。

### 機種ごとの曲ファイルは DefleMask に出してもらう

DefleMask は手元にある(**起動したことがないので、この際使う**)。
**VGM / GBS / NSF / ROM / SID / WAV へ書き出せる**ので、ドライバを自分で書かずに済む。

**ただし DefleMask は VGM を取り込めない。**
「VGM を出せば、あとは各自の形式へ」という道は**通らない**。渡すのは別の形になる。

- **.dmf(DefleMask のプロジェクト)** — 音色もチャンネル割りも渡せる。**本命**
- **MIDI** — 取り込めるが、**音色やチップの都合は落ちる**

つまり書き出しは **VGM(聴いて確かめる用)** と **.dmf(機種へ降ろす用)** の 2 本立てになる。

MSX(AY-3-8910)は DefleMask の対応から外れている可能性がある。
その場合の受け皿として **Furnace**(無料、.dmf を読み、対応チップが多い)を見ておく。
**どちらも要確認。**

### ゲームへ渡す — 音に合わせた演出

**ゲーム中に、音楽に合わせて何か演出したい。**

ゲームへ持っていくのは**生の MML に変換したもの**(一部を除く。
**盛り**は MML に落ちないので行かない)。そのうえで、
**再生エンジンがイベントを送れるようにする。**

- **印は MML の中に埋める。** 持っていくのが MML 1 本なので、
  印を別ファイルにすると 2 つ持つことになる
- **既存のコンパイラは未知の文字を無視する**([mml.js](../engine/mml.js) の末尾)。
  だから**印の記法を足しても、今までの MML は壊れない**
- 送る中身は**絵の側へ渡すデータと同じもの** — キックの位置、拍と小節、
  区間の変わり目、転調の瞬間、雰囲気(テンション)の段。
  違いは**書き出しか、実行時か**だけ
- 受け取りは、**送りつける**だけでなく**「今どこか」を問い合わせられる**ようにしておく。
  ゲームは毎コマ回っているので、問い合わせのほうがずれにくい。
  内部が「今どこか」を持てば、送信はその上に乗る
- **ポーズに追従する。** engine は `pauseBGM` / `resumeBGM` を持つので、印も同じく止まる

分担ははっきりしている。**印を置いて焼くのがツールの仕事、送るのがエンジンの仕事。**

### 絵の側へ渡す(YouTube / Blender / After Effects)

**作った曲を YouTube に上げていきたい。**
動画のエンコードも映像制作もやらない(ルール 8)。**素材とデータだけ出す。**
どれも**もう持っている情報から作れる**。

- **音** — WAV / MP3
- **チャンネルごとに分けた音(ステム)** — 1 声ずつレンダリングすれば出せる。
  動画側で自由に混ぜたり、声ごとに見せたりできる
- **オシロスコープ用のデータ** — チップチューン動画の定番の見せ方。
  ふつうは鳴らしながら録って波形を拾うしかないが、
  **この道具は何をどう鳴らしたか全部知っている**ので、そのまま出せる
- **区間と進行のタイムライン** — チャプターや字幕に使える
- **概要欄のテキスト** — 想定機種・テンポ・拍子・使った進行。全部プロジェクトが持っている

エンコードは既存の [movie.bat](../movie.bat) / [rec2mp4.mjs](../tools/rec2mp4.mjs) の側に任せる。

**Blender や After Effects へはデータで渡して、向こうで盛る。**

**周波数分解は向こうだけでできる**ので、渡さなくてよい。
渡す値打ちがあるのは、**音を解析しても復元できないもの**。

- **ドラムの位置** — **まずここ。これだけで連動した MV が作れる。**
  いちばん小さくて、いちばん効く
- **コード進行**(原型と置き換え後の両方)
- **区間の切れ目と役割**、そして**転調の瞬間**。転調で絵が変わるのは強い
- **拍・小節・拍子**の正確なグリッド(音から推定しなくてよい)
- **どの声が何を鳴らしているか**(旋律 / ベース / 打楽器、音の始まりと終わり)
- **曲のテンション** — **新しく作らなくてよい。「雰囲気」パラメータがすでにそれ**
  (静か / 盛り上げ / 終わった感じ)。曲を通した強さのカーブとして出せる
- **マスクで消えた音** — 鳴っていないが本当はあった音。絵の側では使える

全部テキストで出せる(ルール 4)。Blender は Python、AE は JSON で読める。

**ループの書き出し**(形式ごとに変わる)

- ループ点を持てる形式は、その仕組みに乗せる
- 持てない形式は **N 回展開して、最後に終わりの部分**
- **フェードアウトで終わる**型も用意する(同じパーツをループさせながら落とす)

`renderTracks` はすでに `loops` を取る作りになっている。フェードは `fadeOutBGM` がある。

## DTM へ渡す

**作曲はこの道具でやり、発表する曲は DTM で盛って仕上げる。**
安価または無料のメジャーな DTM を対象にして、持って行ける線を作っておく。
DTM ソフトは手元にあるが使っていない。持っているのは **KORG Gadget 3** と
**GarageBand**(こちらは優先度低い)。

**ただし Windows の Gadget 3 はプラグイン(VST2/VST3)だけで、単体のアプリが無い。**
単体で動く Gadget は macOS と iOS のみ。つまり Windows では Gadget は
**ホストの DAW の中で鳴らす音源**であって、曲を持ち込む先そのものではない。
持ち込む先は Cubase / FL Studio / Ableton Live / Studio One といった**ホスト側**になり、
Gadget はそこで割り当てる音源として効いてくる。

**ホストは Reaper をメインに実装を進める**(Windows / Mac / Linux 全部で動くので、
開発を Linux・Mac・クラウドへ寄せる方針と合う)。
ただし**手元に無いのでテストはできない**。
**テストはサブの KORG Gadget で進める。**

**macOS 版も持っている。** Mac なら単体の Gadget がそのまま持ち込み先になるので、
開発を Windows から離す話(下記)とつながっている。

- 書き出しデータに、**そのツールで盛るときのやり方のヘルプテキスト**を同梱する
- **盛るのに要るその他のデータがあれば、書き出しのときに一緒に出す**

**この道具は DAW が持っていないものを知っている。** そこが渡す値打ちになる。

- コード進行(**素直な原型と、置き換えたあとの両方**)
- 区間の区切りと役割(イントロ / 本体 / 締め)、区間ごとの調と音階
- 部品の役割(旋律 / ベース / 打楽器)と、分野・雰囲気
- テンポ、拍子
- 打楽器の役割とノートの対応(バスドラ / スネア / ハット …)
- 音色の意図 — 汎用音色を **DAW 側で何に置き換えるか**

最後のものは、機種向けの**音色の変換表と同じ仕組み**で作れる。
DTM も「出せない音色を近いものへ振り替える出力先」のひとつとして同じ列に並ぶ。

## 外からの口

- **AI はツールに載せない。** かわりに **MCP や API で外から操れる口**を用意する
- したがって**画面の下に、画面なしでも全部できる芯がある**形になる
  (部品の登録・組み立て・エフェクト・書き出しが、全部その口から叩ける)。
  別リポジトリにする芯の姿とも合う
- **MML ベースだから AI が扱いやすい** — テキストのまま渡せる

```
  │                        区間(調 / 音階 / 拍子)          │
  │                        組み立て表・フィルタ            │
  │                        生成規則・シード                │
  │  2. 部品               部品箱(C / 基準拍子 / 拍数 /    │
  │                        分野 / 雰囲気 / タグ)           │
  │  1. MML                compileMML  文字列 ⇄ イベント列 │
  └──────────────────────┬────────────────────────────────┘
                         │
                    鳴らす層(Web Audio)
                    画面からも、ヘッドレスからも同じものを使う
```

**きもは 1 つだけ — 焼くのは 1 か所。**

どの出力も層 4 を通す。**そこを通らない道を作らない。**
これが「原型を壊さない」の担保で、**抜け道を 1 つ作った瞬間にルール 2 が死ぬ**。

あとは自然に決まる。層 1 は既存の `compileMML` を持ってくる
(**サウンドを別リポジトリへ切り出すときの割れ目もここ**)。
鳴らす層は芯の外で、ブラウザが要るのはそこだけ。

### 作る順番

構成よりこちらのほうが効く。

1. **部品を並べて MML が出る**(層 1 + 2 + 4 の最小形)
2. **鳴らす** — 既存の `PSGPlayer` をそのまま使う。**ここで何か鳴る**
3. **MCP の口** ← ここから制作フローが回りはじめる
4. **曲の層**(進行・区間・フィルタ)— AI と一緒に育てる
5. **書き出し**(VGM → .dmf)
6. **画面** ← 最後

**3 が分水嶺。** そこから先は「ライブで部品を作って鳴らす」フローに乗るので、
作りながら口を育てられる。逆に 1〜2 は自分で書くしかない。

**画面が最後なのはルール 5 から出てくる。**
芯が固まる前に画面を作ると**画面の都合が芯に染み出す** —
画面で扱いやすい形にデータが寄っていき、CUI と MCP が後付けになる。
制作フローは画面なしで回るので、**待てる**。

### 画面(VIEW)は差し替えられるようにする

**最終的には、見た人が引くような UI にはしたくない。**
ただしそれを考えていると先へ進まないので、**最初は開発しやすい VIEW にする**。
そのうえで**あとから VIEW ごと切り替えられるようにしておく**(大原則そのまま)。

そのために要る条件は 1 つ。**画面は芯に触らず、芯の口だけを叩く。**
そうすれば GUI を丸ごと差し替えても芯は無傷で、
**開発用の素朴なビューと、見せる用のビューを並存させられる。**

最初の VIEW は既存の [tools/](../tools/) の実験台と同じ作りでよい —
素の HTML、等幅、表とボタン。
gesture-tool には「まだ作りかけ」と分かる縞の帯まであるので、**家の作法がもう揃っている**。

## 動く場所

**サウンドは先回りしてクラウドで開発できるようにする。**

いまゲーム開発は Windows にくっついているが、そこは Linux / Mac でも動くよう直す。
というより**クラウドで開発できるようにする**。ただしアクションゲームは
ローカルのほうがよいこともあるので、**ゲーム側がどちらになるかは未定**。
サウンドは先に出せる。

**ツールは CUI モードでも動く。** 書き出しもライブラリの追加もそこからできる
(構想はまだ)。MCP・API・CUI・画面は、**同じ芯の 4 つの顔**になる。

**CUI で 1 から曲を作ることは考えない。**
既存のものの設定を変えて何かする、という使い方になる。

**ここで芯は 2 層に割れる。**

1. **純粋な計算の層** — MML のコンパイル、部品、組み立て、フィルタ、進行、マスク、
   MML / MIDI / VGM の書き出し。**どこでも素で動く。** CUI もクラウドもここは通る
2. **音を出す層** — Web Audio でノードを組んで鳴らしているところ。ブラウザが要る。
   WAV / MP3 の書き出しも今はここに乗っている(`OfflineAudioContext`)

1 の層だけなら何も要らない。MML / MIDI / VGM / .dmf は CUI でもクラウドでも素で出せる。

**WAV を出すときだけ 2 の層が要る。そこは画面を持たないブラウザ(ヘッドレス)を使う。**
`OfflineAudioContext` は音の出口を使わない計算なので、ヘッドレスでもそのまま動く。

きもは足場が埋まることではなく、**鳴らす層のコードが 1 つで済む**こと。
聴いた音と書き出した音が同じコードから出る。自前のレンダリングをもう 1 つ書くと、
エンベロープの端やエコーの重なりあたりで**必ず少しずつずれていき**、しかもそれは
「書き出したときだけ変」という一番気づきにくい形で出る。

払うのは**クラウドの入れ物にブラウザを積む**ことだけ。
Node の Web Audio 実装を使えば軽く済むが、**API の実装が 2 つになる**ので
同じずれの危険が戻ってくる。ヘッドレスのほうが素直。

## 公開とライブラリ

**ウェブで動くツールとして公開する。** 必要なら Cloudflare などへデプロイする。

**公開版はサーバにライブラリを保存しない。** そこで:

- **ライブラリの書き出しと取り込み**を作る。**書き出したものが持ち物**になる
- よくできたものは**デフォルトへ取り込む**(次の版に同梱する)。
  部品箱の充実が目標なので、**この昇格路が部品箱の育て方**そのものになる

ブラウザの中(localStorage)へ置けば同じ機械での続きは残せるが、
機械をまたげず消えることもあるので、**持ち出しは必ず書き出しで**。

保存を持たないぶん、**書き出しの形式がプロジェクトの保存形式を兼ねる**。

**ファイル形式は全部テキストで通す。** プロジェクトもライブラリも部品も。
差分が見えて、AI にそのまま渡せて、git に置ける。

**PCM だけが例外になるが、そこも作り方をテキストで持つ。**
波形そのものを抱えず、**プロシージャルに作る**。作るのは別ツールで補佐する。

エンジンにはすでに前例がある。TALK は録音を一切持たず、カタカナと数値から
その場でフォルマント合成で波形を作っている([talk.js](../engine/talk.js))。
**「録音ではなく作り方を持つ」は、この engine の既存の流儀。**

公開版とローカルの AI チャットをつなぐなら Cloudflare 側に MCP を置く手があるが、
保存を持たない以上、**サーバは計算とファイルの受け渡しに徹する**形になる。

## 制作フロー

**MCP の口を最初に用意する。** 洗練させていきたいので、そこを起点にする。

- 口に足りないところは、**直接 JS を操作**しながら進める
- **ライブで曲パーツを作って、その場で鳴らす**
- **再起動するのは仕組みを更新したときだけ**

作りながら口を育てる形になるので、**芯は再読み込みなしで叩ける状態**に置いておく。

**MCP の口が充実するまではローカルで進める。**
「足りないところは直接 JS を操作」はクラウドの MCP には効かない
(手元のブラウザに対してやるものなので)。口が固まってからクラウドへ移す。

## 課題 — 出だしと終わり

**1. ループの継ぎ目が一番効く**

イントロを持つ曲は、終わりから戻る先が**本体の頭**であってイントロではない。
継ぎ目は「本体の最後 → 本体の頭」で、ここが曲中で唯一、作りながら聴けない場所になる。
**継ぎ目だけを繰り返し鳴らす試聴**が要る。無いと出来上がってから気づく。

**2. 食い込み(アウフタクト)**

頭が拍の前から入る曲は、継ぎ目でも同じ食い込みが要る。
「終わりの最後の 1 拍を削って、頭の食い込みぶんを置く」処理になるので、
**イントロの有無とは別に、本体が食い込みを持つか**を曲が知っている必要がある。

**3. 終わりの型を分類しておく**

書き出しの選択肢と 1 対 1 で対応する。曲の属性として持つ。

- ぶつ切り(場面が変わるので終わらせない)
- 締めの和音で終わる
- フェードアウト
- ジングルへ渡す

**4. イントロ作曲機能は、そのままジングル作りになる**

「キャッチーで少し変な短いもの」は、ファンファーレやゲームオーバーの曲と同じ注文。
エンジンには `playJingle`(BGM を止めずに重ねる短い曲)がすでにある。
**イントロ / ジングル / 終わりの締めを同じ道具で作る**と機能が 1 つで済む。

**5. 出だしは SE と重なる**

面の始まりは「スタート音 → 曲」が重なりがち。
頭に一瞬の間を置くかどうかを曲の属性にしておくと、あとで効く。

**6. エンジンは曲まるごとをループする**

`playBGM` は `_pump` で曲全体を繰り返す。イントロを持つ曲は
「イントロは 1 回、そのあと本体をループ」の形が要るので、
書き出しかエンジンのどちらかで面倒を見ることになる。
