# スクロールの差の考察（M-0 ⑥）

**まだ作らない。** どこが「あとで死ぬ」かだけ先に見きわめる。
2026-08-22 時点。[TODO.md](TODO.md) の M-0 ⑥ から来た。

前提は ④（当たりの丸め）と同じ形。
**見た目と論理で別々に丸めを持つと、片方だけ直したときに黙って食い違う。**
④ では当たりで実際に起きかけていた。スクロールでは**まだ**起きていない ——
このゲームは世界が動かず、背景は飾りだからだ。次のゲームで起きる。

## いまどうなっているか

レイヤーごとに `snap` を持っている（`engine/video.js`）。

| | 値 | 意味 |
| --- | --- | --- |
| `layer.snap = 0` | 既定 | 滑らかに動かす |
| `layer.snap = 8` | | 表示を 8 ドット単位に量子化する |

STAR FABLE は星空 3 枚と `neb` の 4 枚に `8` を入れている（`game/main.js:578`）。
速さはレイヤーごとの小数（`-0.25` / `-0.9` / `-2.0`）。

揺れは**別の口**で、`mmsxx.setAdjust()`。画面全体を **1 ドット単位**でずらす
（実機の SET ADJUST 相当）。こちらは丸めない。
8 ドットで動く背景の上に 1 ドットの揺れが乗るのは、実機でもそうなので正しい。

## 1. 「8 ドットかどうか」の 1 つの数では足りない

機械ごとに、粒度がそもそも一様ではない。

| 機械 | 縦 | 横 |
| --- | --- | --- |
| MSX1 | レジスタが無い。名前テーブルを書き換えるので実質 8 ドット | 同じく 8 ドット |
| MSX2 | **1 ライン単位**のレジスタがある | 8 ドット単位 ＋ adjust で ±7 |
| ファミコン | 1 ドット | 1 ドット（ただし属性は 16 ドット単位） |
| PC-88(V1) | テキストは行単位、グラフィックは実質なし | — |

**MSX2 だけで縦と横の粒度が違う。**いま `snap` は 1 つの数なので、この機械を
そのまま表せない。分けるなら `snapX` / `snapY`。これは安い。

## 2. 論理の位置と、見えている位置がずれている

`scrollX` / `scrollY` は**小数のまま**持っていて、丸めているのは `render()` の中だけ
（`engine/video.js:1970`）。だから

- ゲームが読める `scrollY` … 小数。滑らか
- 実際に描かれている位置 … 8 の倍数

が**最大 7 ドットずれる**。そして**描かれている側を読む口が無い**。

このゲームは背景が飾りなので誰も困らない。困るのは世界がスクロールするゲームだ。
敵をワールド座標で置いて画面座標に直すとき、丸めた scroll で引かないと、
**敵だけが 1 ドット単位で滑って背景と食い違う**。そのときゲーム側に
`Math.floor(scrollY / 8) * 8` を書くことになる —— ④ で消したばかりの写しが、また生える。

**打つ手**: 描かれている位置を読む口をエンジンが出す（`layer.viewX` / `viewY`）。
式は `snapTo()` が既に持っているので、新しく書くものは無い。安い。

## 3. 丸める場所が `render()` の中にある

いまは合成しながら丸めている。つまり**画面を描かないと丸めた値が決まらない**。
ヘッドレスで回帰試験を取るとき、これは ④ と同じ形の穴になる
（世界がスクロールするゲームでは、scroll は飾りではなく進行の値になる）。

**打つ手**: 丸めるのは `scroll()` を書いた時点か、読み出しの口で。
`render()` は決まった値を使うだけにする。中くらいの手間。

## 4. 誰が `snap` を決めるのか

④ で線を引いた ——「**見た目は機械、当たりはゲーム**」。
スクロールの丸めは**機械の側**にある。
いまゲームが `far.snap = 8` と 4 行書いているのは、⑤ の機械プロファイルが無いからで、
本来の持ち主ではない。

⑤ が入ったら、`snap` の既定は機械から来て、ゲームは**視差の速さだけ**を言う形にする。
**逆にしない**（ゲームが機械の都合を宣言する形にすると、機械を替えるたびに全ゲームを直す）。

## 5. 裏画面が 2 の冪しばり —— ここがいちばん高い

`checkVirtualSize()` が **2 の冪しか許さない**。
回り込みを `vx & (w - 1)`、行の先頭を `y << log2(w)` で出しているからだ
（合成の内側ループ。星空のセル飛ばしとも絡んでいる）。

ところが

- ファミコンの名前テーブルは 256 x **240**
- PC-88 は 640 x **200**

**どちらも 2 の冪ではない。**いまの作りでは、この 2 つの機械の
「実機どおりの回り込み」が表現できない。

手は 2 つ。

- **a. 回り込む範囲だけ別に持つ**（`wrapW` / `wrapH`）。
  マスクが使えなくなって剰余になるので、内側ループがそのぶん遅くなる
- **b. 機械ごとに「回り込みは使わない」と宣言**して、継ぎ足しはゲーム側でやる

**先に決めておくべきなのはここだけ。**あとから `& mask` を剰余に変えるのは
合成の内側ループを触ることになり、速さの作り込み（セル飛ばし・走査線）と噛み合っている。
ほかの項目は口を足すだけなので、いつやっても値段が変わらない。

## 6. 速さと丸めの噛み合わせ

`snap = 8` で小数の速さを与えると、**絵が動く間隔は割り切れないかぎり不揃いになる**。
いまの 3 枚を数えるとこうなる。

| レイヤー | 速さ | 1 マス動く間隔（コマ） |
| --- | --- | --- |
| `far` | -0.25 | 32, 32, 32, … |
| `mid` | -0.9 | 9, 9, 9, 9, 9, 9, 9, 9, 9, **8**, … |
| `near` | -2.0 | 4, 4, 4, 4, … |

`mid` だけ 10 回に 1 回つまる。実機でもこう見えるので不具合ではない。
ただし **`snap = 0` の機械に移すと `mid` だけ印象が変わる**（ほかは割り切れるので変わらない）。

速さを「何コマで 1 マス」で宣言できれば、どちらの機械でも同じ意図が出せる。
**今すぐ要るものではない。**そういう口があり得る、という記録。

## 7. 入れないと決めるもの

**名前テーブルを書き換えて動かす**（MSX1 の本当のやり方）は**やらない**。
重いし、ここまでやっても得られるのは「速いスクロールができない」という制約だけ。
演出として欲しくなったらそのとき個別に書く。標準の口にはしない。

⑥ に書いた「**無理はしない**」はこれのこと。

## まとめ —— 先にやる順

1. **裏画面の 2 の冪しばりをどうするか決める**（5）。あとが高いのはここだけ
2. 丸める場所を `render()` の外へ出す（3）。④ と同じ形の穴をふさぐ
3. `snapX` / `snapY` に分ける（1）、描かれている位置を読む口（2）。どちらも安い
4. `snap` の持ち主を機械へ移す（4）。⑤ 待ち
5. 速さの宣言のしかた（6）は、必要になってから

1 と 2 が済んでいれば、世界がスクロールするゲームを始めても死なない。
3 以降は始めてからでも足せる。
