## 合成音色(まだ仕様は決めていない)

**1 つの名前で、複数の音を重ねて鳴らせるようにしたい。**

いまは重ねたい音の数だけトラックを書いている。`beat`（[demotunes.js](../engine/util/demotunes.js)
の `beatTune()`）では、FM の打楽器が細いのでノイズと矩形波を同じ位置に置いており、
**同じリズムを 3 回書く**ことになっている。和音も 1 本では鳴らせないので
3 トラックに分かれている。これを音色の側で持てれば、MML はぐっと短くなる。

重ねたいものの例:

- 打楽器 + ノイズ(胴鳴り・空気)
- 基音 + 倍音(オクターブ上、5 度上)を混ぜて厚みを出す
- 同じ音を少しずらして重ねる(デチューンは `@d` で済むが、音色ごと変えたい)

決めていないこと: 重ねる音ごとの音量差・高さのずらし・エンベロープを
別々に持てるか、トラック数(発音数)の数えかたをどうするか。

## K-2. プレイ動画

遊んだところを動画にして出せるようにする。**まだ着手していない**。

| 決めごと | 内容 |
|---|---|
| 録りかた | `MediaRecorder` + `canvas.captureStream()`。**外部ツールも許可も要らない** |
| 音 | ミュートで作ったマスターから分岐して混ぜる |
| 大きさ | 3 倍のオフスクリーンへ毎コマ写してから録る(264x200 のままでは小さい) |
| 公開版 | **公開版でも使える**。webm が作れない環境(Safari)ではボタンを出さない |
| 長さ | やられる直前の 30 秒。上限も決める |

### 直前の 30 秒をどう残すか

webm は**先頭の切れ端だけが「何の動画か」を持っている**ので、古い切れ端を捨てる
やりかたでは再生できないファイルになる。手は 2 つ。

1. **録画を 15 秒ずらして 2 本走らせる**（すぐできる）。どの瞬間でも
   どちらかが 15〜30 秒ぶんを 1 本の正しいファイルとして持っている
2. **操作を記録して再生する**（きれい。長さもきっかり決まる）。
   そのためには乱数を種つきにする必要がある

### 乱数を種つきにする(1 と 2 の両方に効く)

- **エンジン側に持たせる**。`mmsxx.rng.seed() / next() / int() / save() / restore()`
- **ゲームに効くところだけ**種つきにする。爆発の粒や画面揺れなど**見た目はそのまま**
  (`main.js` の `Math.random()` 101 か所のうち、効きそうなのは 34 か所ほど)
- 記録に残すのは `{ seed, build, keys: [[コマ番号, キー], ...] }` だけ。30 秒で数キロバイト

**決めごと**:

- 記録は**その場で動画にするための一時的なもの**。長く取っておくものではない
- 記録に**版番号(`BUILD.version`)を入れる**。違う版なら再生を断る
  (コードが 1 行変わるだけで再現できなくなり、しかも**黙って壊れる**ため)

### いまの作り(できあがっている)

**画面を溜める方式**にしてある。エンジンが**色番号のまま**輪っかに溜め、
ゲームは何秒ぶん持つかを決めるだけ。

```js
mmsxx.keepFrames(3);   // 直前 3 秒(ゲーム側は SHARE_KEEP_SEC の 1 か所)
mmsxx.frameAgo(1);     // 1 秒前にいちばん近いコマ
mmsxx.frameBackCanvas(0);   // 番号で取り出す(リプレイ用)
```

- 1 コマ 51.6KB、**60fps で 3 秒なら 9.1MB**（色に直したものの 4 分の 1）
- **60fps で溜める**。30fps だと点滅するキャラが消えたコマを拾ってしまう
- シェアの 1 枚もここから取る（`frameAgo(1)`）
- **リプレイの再生（溜めたコマを順に出す）はまだ作っていない**

### 先の話 — 状態の写しで置き換えられる

**状態の写し（乱数の進み具合を含む）+ そこからのキー操作**があれば、
画面を溜めなくても最後の数秒を作り直せる。**数十キロバイトで済む**。

| | 画面を溜める（いま） | 状態の写し |
|---|---|---|
| 大きさ | 9.1MB | 数十 KB |
| 音 | 鳴らない（絵だけ） | **鳴る**（作り直すので） |
| 見た目 | **見たままと完全一致** | 爆発の粒などは少しちがう |
| 手間 | ゼロ | 種類ごとに書き出しと組み立てが要る |
| 続きを遊ぶ | できない | **できる** |

**引っかかるのは、状態にスプライトの実体が混ざっていること。**
敵も弾も `{ sp, vx, vy, ... }` の形でスプライトそのものを抱えているので、
写すときは「どの絵か・どこにいるか」へ開いて、戻すときに作り直す必要がある。
しかも**ゲームを直すたびに手当てが要る**（忘れると黙って壊れる）。

**進めかた**:

1. いま … 画面を溜める（できあがり）
2. 次 … 状態の写し（**続きを誰かに遊んでもらう**ため。こちらが本題）
3. そのとき … リプレイも写し方式へ寄せて、画面の溜めをやめる

スマホで 9.1MB が重いと分かったら、2 を前倒しする理由になる。
乱数を種つきにしてあるので、2 の半分はすでに済んでいる。

## L. 絵の書き出しと取り込み

### いまの作り(できあがっている)

**絵を画像として書き出す**道具(`engine/util/artexport.js`)。開発用。

```js
exportSymbol(mmsxx, SPRITE_SYMBOLS.player, { scale: 4 });     // 1 枚
exportSheet(mmsxx, SPRITE_SYMBOLS, { scale: 2, width: 512, padding: 4 });  // まとめて
downloadArt(canvas, 'sheet.png');                              // 落とす
```

開発版のコンソールからも呼べる。

```js
mmsxxArt('player', 4)           // 1 枚を 4 倍で
mmsxxSheet('sprite', 2, 512)    // スプライトを 2 倍で 512 ドット幅に並べて
mmsxxSheet('bg', 1, 1024)       // BG も同じように
```

- 倍率は整数倍(ドットはぼかさない)
- まとめて並べるときは**いちばん大きい絵に合わせた升目**に置く。余白と幅を決められる
- 色は**画面と同じパレット**から引く。色合いを切り替えて書き出せば、その色のまま出る
- 透明(色番号 0)は透けたまま残る

### V2 でやること

- **索引(JSON)を一緒に書き出す**。**TexturePacker や Tiled と同じ形**にしておくと、
  外の道具でそのまま開けて、直したものを**読み戻して素材を入れ替えられる**。
  - TexturePacker の JSON(hash) … `frames` に「名前 → 場所と大きさ」を並べる形。
    名前で引けるので入れ替えに向く
  - Tiled のタイルセット … 升目の大きさがそろっていれば、そのまま読める。
    いまの並べかた(いちばん大きい絵に合わせた升目)はこれに合っている
  - どちらも同じ並びから作れるので、**書き出しは 1 回、索引だけ 2 通り**にできる
  - 索引には**倍率・余白・升目の大きさ・色合いの名前**も入れておく
    (読み戻すときに、何倍で書き出したものかが分からないと戻せない)
- **名前を焼き込む**。一覧として見るときに、どれが何か分かるようにしたい
  (いまは絵だけ。字を入れる場所と大きさの決めごとが要る)。
  索引に名前が入るので、**焼き込みは見るためだけ**のものになる
- **外で直した絵を取り込み直す流れ**。書き出す → 外の道具で直す → 取り込む、をひと続きにする
- **フルカラーの絵を取り込んで変換する流れ**。減色と「横 8 ドット 2 色」への均しを、
  取り込みのところでやる(いまは makedata.mjs にコードとして描く方式だけ)

### 1. 機械を切り替えられる仕組み（大工事）

**仕組みだけ入れる。中身の実装はまだしない。**
MSX 以外（ファミコン、PC-88 の 3 プレーンなど）を**受け止められる形**にしておく。

- スプライトの無い機械は、**よしなに解釈**できるとよい。難しければ無理をしない
- 当面は MSX で作り続ける。切り替えの口が空いていればよい

### 2. スクロールの差

8 ドット単位のスクロールなど、**ハードウェアで持っている機械と持っていない機械**が
無理なく切り替わるとよい。ただし**無理はしない**。

**困ったら MSX の再現を優先**し、ほかの機械の表現はゲーム側で独自にやる。

### 3. ビュー無しモード

画面を作らずに回せるようにする（M-5）。**難しいのは当たり判定**。

- いまの当たりは**見た目に追従している**ところがある
  （BG スプライトが 8 ドットに丸まるので、判定も `snap8` した値で取っている）
- ビューが無いと 8 ドット吸着が無くなるので、**当たりごとに「どちらを見るか」を決める**
  必要がある … 見た目に合わせる / 数のまま
- ここを宣言で持たせると、機械を替えたときも同じ理屈で通る

## M-1. 状態機械(StateMachine)

いまは `mode` / `stage` / `act` / `timer` / `hide` / `telegraph` / `wait` が
ボスごとにばらばらで、**どの組み合わせが何の局面か**が当たり判定の側にも写っている。
(例: 突進中の判定が `rage && hide<=0 && telegraph<=0`。
「顔を出すときも大ダメージが残っていないか」を確かめるのに、3 か所を読む必要があった)

```js
const fsm = new StateMachine({
  spiral: { update: ..., after: 300, next: 'leave' },
  leave:  { update: ..., when: (b) => b.offScreen, next: 'hide' },
  hide:   { for: 60, next: 'peek' },
  peek:   { for: 200, cues: { 150: 'count3', 100: 'count2', 50: 'count1' }, next: 'charge' },
  charge: { update: ..., when: (b) => b.offScreen, next: 'return' },
  return: { for: 90, next: 'spiral' },
});
fsm.is('charge')           // 当たり判定はこれだけ見る
fsm.in('peek', 'return')   // 「硬い」局面をまとめて書ける
```

- **状態の名前が 1 か所にしかない**のが肝。局面ごとの調整が 1 行で済む
- `fsm.toMermaid()` で**図を吐く**。仕様書が古くならない(下の M-6)
- 開発中は画面の隅に「いまの状態・残りコマ・次の行き先」を出す。
  `mmsxxState('charge')` で飛べるようにする(いまは `mmsxxKing('man')` だけがある)

## M-2. 当たりの表(HitMatrix)

「誰と誰が当たるか」が `updatePlay()` の中に 10 か所以上ばらけている。
**表にして 1 か所で決める**。

|  | 自機 | 自弾 | 敵 | 敵弾 | ボス | 障害物 | アイテム |
|---|---|---|---|---|---|---|---|
| 自機 | − | − | ● | ● | ● | ● | ● |
| 自弾 | − | − | ● | ▲ | ● | − | − |
| 敵 | ● | ● | − | − | − | − | − |
| 敵弾 | ● | ▲ | − | **?** | **?** | − | − |

● 当たる ／ ▲ 撃ち落とせる弾だけ ／ **? これから足したいところ**

**敵弾どうしをぶつける**のは、この表に 1 マス足すところから始められる。

- 敵弾 60 発なら組み合わせは 1770 通り。四角どうしの比較なので**1 コマぶんとしてはまだ軽い**
- 200 発を超えると効いてくるので、そこからは**格子に分ける**
  (16 ドット四方の升に入れて、隣の升だけ見る)。30 行ほどで書ける
- 安く済ませる道もある。**「ぶつかる弾」だけに印を付ける**
  (いまの「撃ち落とせる弾」と同じ仕組み)。重い弾と軽い弾に分ければ、
  見た目の面白さを残したまま数を抑えられる
- **当たりの順番は座標の順(左上から)で決める**。配列の順に頼ると、
  弾どうしが当たるゲームでは**同じ入力から同じ結果が出なくなる**
  (リプレイと記録の再現性を残すため)

局面ごとの当たりかたも、条件式ではなく表で持ちたい。

```js
boss.hits = {
  peek:   { bullet: 'tough', flame: 'none', body: 'critical' },
  charge: { bullet: 'weak',  flame: 'none', body: 'critical' },
  man:    { bullet: { head: 2, body: 1 }, flame: 'full',
            body: { head: 'none', body: 'critical' } },
};
```

## M-3. 演出の順番(Sequence)

撃破 → リプレイ → 集計 → エンディング → 登録、の並べ替えに時間がかかった。
いまは「終わったら呼ぶ関数」を渡し合う形なので、順番を変えると呼び出しの入れ子が変わる。

```js
seq().play(deathBlast).talk('kozorite').replay(4)
     .show(stageResult).wait(960).story(buildEnding).then(enterGameOver);
```

**待ちかた(コマ数・音の終わり・キー入力)を同じ書き方にそろえる**のが目的。
溜め(直前 4 秒のコマと音)を止める場所も、この並びの中で宣言できるようにしたい。
いまは `setPaused(false)` が溜めを戻してしまうので、**止めた理由を持つ印**が要った
(`captureFrozen`)。

## M-4. 部位と持ちもの(Parts)

`bossDefeated()` に `removeSprite` が 15 行並んでいて、部位を足すたびに書き足している。
片づけ忘れると次のゲームまで残る(青い裂け目がそうだった)。

```js
const parts = new Parts(mmsxx);
parts.sprite('crown', img, { priority: 12 });
parts.bg('seg', img, { count: 12 });
parts.remove();      // 何を持っていても全部片づく
```

`SpriteCombo`(色ごとに分けたスプライトをまとめる部品)は、この下位部品として収まる。

## M-5. 画面なしで回す(ヘッドレス)

エンジンから**描画を外して回せる形**にする。

- `mmsxx.step()` を 1 コマぶんの更新として切り出し、描画は別の関数にする
- 試験では `step()` を 10000 回まわし、**状態機械が詰まらないか**を見る
  (どの状態にも入れるか・抜けられるか)
- **片づけ忘れの検出**。終わったあとにスプライトと BG スプライトの残数が 0 かを数えるだけで、
  「裂け目が次のゲームに残る」たぐいは自動で見つかる
- 入力を配列で渡せば、**1 面クリアまでの操作を記録して回帰試験にできる**
  (乱数の種は記録に残っているので、同じ出かたを再現できる)

## M-6. 図で確認する

**コードではなく図で構成を確かめたい**。状態を宣言で持てば、図はそこから出せる。

- `fsm.toMermaid()` が Mermaid の文字列を返す → `docs/` に貼れば GitHub がそのまま描く
- 出すのは 3 種類: **状態の遷移** / **面が終わるときの流れ** / **当たりの表**
- 人が書いた図は古くなるが、**宣言から出した図は古くならない**

## M-7. 体力と合図(Meter)

「体力が 4 分の 1 を切ったら座る」「8 割で船が壊れる」が更新処理の中に `if` で埋まっている。
今回の「弾で削られたときだけ座る」は、**体力の減少に「誰が削ったか」が付いていなかった**ので
足す場所を探すのに時間がかかった。

```js
boss.hp = new Meter(480, { at: [
  { below: 0.25, by: 'bullet', do: (b) => b.fsm.go('meditate') },
  { below: 0.20, do: breakShip },
] });
boss.hp.damage(12, { by: 'flame' });   // 誰が削ったかを一緒に渡す
```

## M-8. 音と動きの同期(Cue)

「3・2・1 の声が鳴り終わってから突っ込む」を、コマ数の直書き(`telegraph === 150`)で
合わせている。声の長さを変えるたびに数字を直す必要がある。
**声の実長から逆算**できるようにしたい。

## M-9. 機械の仕様を差し替えられるようにする（優先度：高）

**MSX1 前提のまま進めるが、あとからファミコンへ切り替えやすい形にしておく。**
決まりごとをコードに直接書かず、**機械の仕様として数字で持つ**。

```js
const MSX1 = { cellW: 8, cellH: 1, colorsPerCell: 2, spritesPerLine: 4, spriteColors: 1, screen: [256, 192] };
const FC   = { cellW: 8, cellH: 8, colorsPerCell: 4, attrBlock: 16, spritesPerLine: 8, spriteColors: 3, screen: [256, 240] };
const MD   = { cellW: 8, cellH: 8, colorsPerCell: 16, spritePixelsPerLine: 320, spriteColors: 15, screen: [320, 224] };
```

### 機械ごとの数字

| | MSX1 | ファミコン | PCE | GB | GBC | メガドラ | SMS/GG |
|---|---|---|---|---|---|---|---|
| 画面 | 256x192 | 256x240 | 256x224 | 160x144 | 160x144 | 320x224 | 256x192 |
| 同時発色 | 15+1 | 25 | 241 | 4階調 | 56 | 64 | 32 |
| 色の単位 | **横8ドット2色** | 8x8で4色（**組は16x16単位**） | 8x8で16色 | 画面で4階調 | 8x8で4色 | 8x8で16色 | 8x8で16色 |
| 1行の枚数 | 4 | 8 | 16 | 10 | 10 | **20（実際は横320ドット）** | 8 |
| 全体の枚数 | 32 | 64 | 64 | 40 | 40 | 80 | 64 |
| 1枚の色数 | 1 | 3 | 15 | 3 | 3 | 15 | 15 |
| 音 | 矩形3+ノイズ | 矩形2+三角+ノイズ+PCM | 波形6 | 矩形2+波形+ノイズ | 同左 | **FM6(4op)**+矩形3+ノイズ | 矩形3+ノイズ(+OPLL) |

**MSX1 がいちばん厳しい**ので、いまの素材はどの機械へ持っていっても通る。

TMS9918 を積んだ機械（**SG-1000 / SC-3000 / ColecoVision / Sord M5**）は
**画面まわりが MSX1 と同一**。音源の系統（AY-3-8910 か SN76489 か）だけが違う。

### 直すところ（軽い順）

| 何を | どこ | 重さ |
|---|---|---|
| 色の引き表が **16 固定**（`pal32 = new Uint32Array(16)`） | エンジン 1 行 | 軽 |
| スプライトの枚数・色数の検査 | 仕様の数字にする | 軽 |
| 画面の大きさ・スクロール | 同上 | 軽 |
| 1 行の制限を**ドット数**でも数える（メガドラ用） | `_drawSprites` | 中 |
| 色制限の形（8x1 → 8x8 + 16x16 の組） | `_enforceRuns` を差し替え可能に | **中** |
| **色番号がゲーム側に散っている**（`hud.print(..., 15)` など） | ゲーム全体 | **重** |

色は `engine/util/colors.js` を**用意だけしておき、使うかはゲーム側に任せる**
（`C.WHITE` のように名前で引く）。MSX2 でも AA 表示でも要るので、
どの方向へ進んでも無駄にならない。

`MID_TONES`（横 8 ドット 2 色を逆手に取った中間色）は **MSX1 専用の道具**として分ける。

### 対象外

- **スーパーファミコン / Amiga** … 音がサンプル再生。回転拡大もあるので別枠
- **Atari 2600** … 走査線を追いながら 1 行ずつ作る機械。画面という単位が無い
- **X68000 / ネオジオ** … 制限が緩く、「制限が味になる」ところが残らない

## M-10. 音源をワークレットへ移す（優先度：高）

**4 オペ FM とビープを入れるための工事。まとめてやる。**

いまは Web Audio の部品（発振器と音量）を並べて、先の時刻に予約している。
この作りでは次の 2 つができない。

- **帰還のある FM**。グラフを輪にするには遅延節が要り、その最小が 128 サンプル（約 3 ミリ秒）。
  音の周期より長いので帰還にならない。**帰還は FM らしさの半分**（明るい音・金属質な打楽器）
- **1 ビットへ潰す**（ビープ）。混ぜかたの段が要る

### 録画・溜めへの影響は無い

```
曲・SE ─→ _bus ─┬─→ _master ─→ スピーカー
                 ├─→ 聞き耳(AudioWorklet) … 直前 4 秒を溜める
                 └─→ 録画の口(MediaStreamDestination)
```

**録画も溜めも `_bus` から取っている**ので、その手前で何を使っていようと関係ない。
AudioWorklet 自体は**すでに使っている**（聞き耳がそれ）。
変わるのは「音を予約するやりかた」だけで、`_scheduleTrack` まわりの書き直しが工事の本体。

### 入れるもの

- **4 オペ FM**（オペ 4 つ + 結線 8 通り + 帰還）。計算そのものは 200 行ほど、演算量も軽い
- **音色ファイルを読む**。`.tfi` / `.opm` は 30 行ほどで読める。
  4 オペは 1 音色 35 個ほどの数字があり、耳で合わせるのは無理なので、**既存の音色を借りる**

  **変換はすべて素材を作るときに 1 回。ランタイムにコンバータは載せない。**
  `tools/` に置いて、出力はいまの MML と音色定義の形にそろえる
  （`assets-src/makedata.mjs` と同じ並び）。

  | 元 | どうする |
  |---|---|
  | `.tfi` / `.opm`（音色） | **変換する**。最優先。費用対効果が段違い |
  | **MSX の駆動系の MML**（MGSDRV の MGSC、MuSICA など） | **対応したい**。文字 → 文字 |
  | MIDI / 他の MML（PMD・ppmck など） | 気が向いたら。音符が入っているので難しくない |
  | **VGM など** | **対応しない**。レジスタの書き込み記録なので音符が無く、採譜の仕事になる |

  MSX の駆動系は、**MML のソースが残っているものだけ**を対象にする。
  コンパイル済み（`.mgs` など）は駆動系の命令表が要るので追わない。
  変換で決めることになるのは 4 つ:

  1. **音色番号の対応**。向こうの `@1` は駆動系が持っている音色。**対応表を人が作る**
     （PSG なら矩形波のデューティ、SCC なら波形メモリへ）
  2. **チャンネルの割り当て**。PSG 3 + SCC 5 + FM 9 のような構成をこちらの音数へ畳む
  3. **駆動系だけの命令**（ソフトウェアエンベロープ・ディテューン・ポルタメント・繰り返し）。
     無いものは近い書きかたへ寄せるか、展開して音符にする
  4. **テンポの単位**。1 秒 60 回の割り込みを基準にしているものが多い

  **曲そのものは作った人のもの**。駆動系がフリーでも、
  配られている曲を公開版に載せるなら許可が要る（手元で試すぶんには問題ない）。

  **難しい曲は音声ファイルで鳴らす**（すでに対応済み。`defineBGM(name, { url })`）。
  出口は同じ `_bus` なので、録画にもリプレイの音にも入る。

  変換の検算には WAV 書き出し（`mmsxxExportWav` / `game/wavexport.js`）を使い、
  `npm run checkbgm` の隣に置けば回帰試験になる。
- **1 ビット出力（ビープ）**。全部足してから符号だけ取る。2 音鳴らしたときの濁りも自然に出る
- **音程の階段**（`psgTune`）を本物どおりに
- **サンプル曲を増やす**。機械ごとに 1 曲ずつ（PSG / ファミコン / PCE / GB / メガドラ / ビープ）

### ビープの API（先に入れてもよい）

ビープだけなら**いまの仕組みのままでも作れる**。`WaveShaper` に
「0 より上なら +1、下なら −1」の曲線を入れれば、そこで 1 ビットになる（20 行ほど）。

```js
mmsxx.audio.defineBGM('title', ['o4 cdefg', 'o3 c'], { beep: true });
mmsxx.audio.defineSE('shot', 'o6 c16', { beep: true });
mmsxx.audio.beepVolume = 0.6;   // 潰したあとに掛ける(機械のつまみにあたる)
```

- 曲の書きかたは**いまと同じ**。トラックを 2 つ書けば 1 本の線を取り合う音になる
- MML の `v` は**デューティの幅**にする。実機のビープ音楽と同じ手
  （潰したあとの波は振幅が一定なので、音量は幅で作るしかない）
- **SE もビープに回すかは選べるように**。実機は線が 1 本なので、
  SE が鳴っている間は曲が濁る。それも味だが、遊びにくくもなる

## M-11. スプライトの無い機械（PC-88 / PC-80 / PC-98）

**スプライトを使わなければ、いまの作りでも作れる。** らしさは別のところにある。

- **RGB の 3 面**。同じ場所へ 3 回書く。書き込みを**1 面ずつ別のコマに散らす**と、
  赤 → 黄 → 白 と色が育っていく、あの見え方になる。1 面だけ消し損ねると青い幽霊が残る
- **仮想スプライト**（保存して戻す方式）。戻し忘れの軌跡、重なりの消し順、
  縦の走査に間に合わないときのずれ（ティアリング）まで含めて癖になる。8 枚もあれば足りる
- **ビープ**（M-10）

ZX スペクトラムは MSX1 の下位互換にあたるので、**ゲーム側の描きかたで再現できる**
（横 8 ドット 2 色を、8x8 のマス 2 色に自分で寄せる）。

# N. 配布のしかた（アプリとして出す）

> 「ウェブでしかできないの？ Windows や Android にインストールできない？」という
> 声をもらった。いつやるかは未定（V2 の前でも後でもよい）。ここは考察だけ。

## 順番は決まっている

- **Android 版はスマホ対応が終わるまで作れない**（触って遊べないアプリになる）
- **Windows 版はいつでも作れる**。キーボードで遊べるので今日やっても成立する

    web のスマホ対応 → PWA → Android
    Windows はその横で、好きなときに

## 選べる包み方

| 方法 | 何が要る | 得られるもの | 重さ |
|---|---|---|---|
| **PWA** | manifest + サービスワーカー + アイコン | Android / Windows で**ホーム画面から起動**、オフライン、全画面 | **1 日** |
| **itch.io** | zip を上げるだけ | ダウンロードの受け皿。web 版もそのまま置ける | **半日** |
| **Tauri** | Rust の道具一式 | Windows の `.exe`（**5MB ほど**） | 数日 |
| **Electron** | Node だけ | 同上（**150MB ほど**） | 数日 |
| **Capacitor** | Android Studio | `.apk`。Play ストアへ出せる | 数日 |

**まず PWA。** いまの作りは静的なファイルだけなので、足すのは manifest とアイコン、
それにサービスワーカーだけ。それで「インストールできますか」への答えが
**Android と Windows については Yes** になる。

iOS と Steam は最後でよい（iOS は Mac と年会費が要り、
「ただのウェブサイトを包んだだけ」の審査基準もある）。

## 先に知っておく引っかかり

1. **ランキングは必ず繋ぐ**。包んだアプリは出どころ（オリジン）が
   `app://` や `http://localhost:1420` になるので、そのままでは弾かれる。
   引っかかるのは 2 か所:

   | | 手当て |
   |---|---|
   | 出どころの許可 | サーバに**包み版の出どころを足してもらう**。Tauri も Electron も出どころを固定できるので、1 つ決めて登録する |
   | **Turnstile** | ドメインに紐づくので通らない。**包み版用に別の鍵を発行**し、サーバ側で web と区別する |

   鍵はアプリの中に入るので絶対の秘密にはできないが、
   いまも「なりすましは防げない、閾値を上げる道具しかない」前提で運用しているので方針は揃う。
   悪用されたらアプリの鍵だけ止められる。**サーバ側（別リポジトリ）と先に相談する項目**。

   **共有は OS に任せる**。`navigator.share` を使えば OS の共有シートが開く
   （Android Chrome / iOS Safari / Windows の Chrome・Edge。**web 版でも今日から使える**）。
   渡すのは画像そのものではなく、**サーバが作ったカードの URL**にする:

   - 画像だけ渡すと、カードのページも OG 画像も使われない
   - URL なら、貼った先が X でも LINE でも Discord でもカードが展開される
   - 投稿先を選べるので X 以外にも広がる

   流れは変えず、最後の口だけ差し替える形:
   絵を作る → サーバへ送る → カードの URL をもらう →
   `navigator.share` があれば共有シート、無ければ いまどおり X の下書きを開く。
   **スマホ対応のときに入れると効く**（いまは X アプリ前提の作りになっている）。
2. **記録が引き継がれない**。ブラウザの保存と包み版の保存は別物。
   持ち出し・取り込みの口を作るか、「別のもの」と割り切るか
3. **`file://` では動かない**（モジュールを読めない。index.html に断りが出る）。
   どの包み方も内部でサーバを立てるか独自の口を使うので、そこは道具が面倒を見る

## ついでに得なもの

**ゲームパッド対応**（Gamepad API）。web でも動くので、包む前に入れておけば web 版でも使える。
デスクトップ版を出すなら、あったほうが自然。

# O. 記録に「何で遊んだか」を残す

**「スマホでこの点」は価値が違う**ので、ランキングに土台と操作を持たせる。
**いまの記録はすべて `pc` / `key` として扱う。**

| 項目 | 値 |
|---|---|
| 土台 | `pc` / `mobile` / `app` |
| 操作 | `key` / `touch` / `pad` |

- **操作は「使ったもの全部」を持つ**（途中で持ち替える人がいる。`key+pad` のような形）。
  一覧に出すのは**いちばん多く使ったもの 1 つ**でよい
- 土台は自動で決まる（`isMobileLike()` と、包み版なら `BUILD.name`）
- 一覧での見せかたは、名前の隣に 1 文字（`K` / `T` / `G`）。土台は色で分ける手もある

## 集めかた

押された瞬間に**1 か所の窓口**を呼ぶだけにする。

```js
markInputSource('pad');   // 押されたときに呼ぶ。数えて、いちばん多いものを記録に載せる
```

**入力を作っているセッション（バーチャルパッド・ゲームパッド）に、
先にこの窓口を呼んでもらう。** あとから両方に手を入れると二度手間になる。

## サーバ側

別リポジトリに項目を足してもらう。**既存の記録は `pc` / `key` 扱い**という前提も一緒に伝える。
